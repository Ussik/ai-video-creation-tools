# 文本模型上下文与输出额度：调研和实施设计

调研日期：2026-11-10。范围为模型提供商配置、能力发现、请求预算、上下文管理与长文恢复。本文是设计建议，未实施代码变更，未修改真实模型配置或发起模型生成。

## 建议结论

保留当前 DeepSeek Harness 风格的提供商与模型表单，补齐内部三层职责：

1. **模型和渠道能力**：这个端点上的具体模型支持多少输入、多少输出，是否共享窗口，数据从哪里来。
2. **用户请求偏好**：默认自动安排、固定输出额度，或明确沿用上游默认；不能与模型硬上限混用。
3. **本次请求计划**：基于最终输入、任务要求、推理消耗规则和能力，确定实际输出参数；不能满足完整交付时调整工作拆分或保留断点。

协议只处理字段和消息编码。Responses、Chat Completions、Anthropic Messages 不决定模型的上下文规则；同名官方模型与中转商模型也不能共用未经核实的能力声明。

## 一、能力信息怎样保存和获取

建议先作为模型 `settings` 中一个版本化对象实现，不为这项功能立即新建一套大型服务或多张数据库表。

```ts
type TextModelLimits = {
  version: 1
  budget_mode: 'shared' | 'separate' | 'unknown'
  context_tokens?: number
  input_tokens?: number
  output_tokens?: number
  output_includes_reasoning: boolean | 'unknown'
}
```

此结构描述限制和计数语义；旁边分别保存发现记录和用户覆盖。每项证据带来源、更新时间、模型版本以及渠道范围（提供商、API 地址、协议、模型 ID）。一个字段的已知值不能使其他字段自动变成已知；输入和输出数值也不能单独证明预算模式。

能力来源按以下顺序解析：

1. 用户针对该渠道的显式覆盖。
2. 渠道自己的能力元数据。
3. 已核对、能精确匹配渠道与型号的维护目录。
4. 未知。

官方原生目录可以直接用于相应官方端点。对于中转同名模型，官方目录只显示为参考，不能直接升级为渠道硬限制。切换地址、协议、模型版本后，旧能力证据不能默认为已验证。

手工覆盖不能伪装成官方发现值。刷新目录只更新发现记录，不能覆盖手工值。用户降低自定义预算属于产品限制；用户声明更高渠道能力也必须标注为手工配置，不能称在线验证通过。

允许“刷新模型与能力”，但只有渠道实际支持对应元数据接口才获取。没有字段时维持未知，不以无依据的 1M、128K 作为已知能力，也不通过自动付费生成试探最大边界。

## 二、模型表单怎样展示

保持现有提供商卡片、模型目录、展开选项的层级，不让正常用户填写 JSON 请求体。

模型选项的普通区域建议显示：

- **可用上下文／最大输入**：共享模型显示上下文，独立预算模型显示最大输入。展示准确数字及来源，允许展开修改。
- **单次最大生成量**：模式为“自动安排”“固定额度”“沿用服务默认”。固定额度使用现有 K／M 输入，并显示精确 Token 数。
- **推理设置**：只提供已声明支持的档位。说明思考是否占生成额度；未知时不做肯定承诺。

“模型支持最多生成多少”属于能力说明；“本次默认限制多少”属于请求设置，视觉上要能区分。不要只靠一个 128K 占位符同时表达两者。

三个输出模式必须有清晰语义：

| 模式 | 行为 |
| --- | --- |
| 自动安排 | 程序结合任务和经确认的能力决定本次实际值，并显示解析结果；不等于省略参数 |
| 固定额度 | 使用用户明确填写的值；超出已确认能力时提示冲突，不能静默调低后继续 |
| 沿用服务默认 | 不发送输出参数；明确说明默认值可能未知，不能保证完整长文输出。协议要求必填时禁用该模式 |

原 `output_reserve_tokens` 暂留高级兼容区，仅用于旧请求没有输出参数时的本地预算估算。标准新配置尽量使用已解析的真实额度，不再要求普通用户分别维护“最大输出”和“输出预留”两个相似数字。

## 三、每次请求怎样计划和检查

统一生成 `TextRequestPlan`，供实际发送、上下文预检、累计用量预留和运行诊断共同使用，避免每层各算一套输出数值。

流程：

```text
读取本次任务的模型／渠道配置快照
→ 解析能力来源与用户输出模式
→ 组装完整消息、工具、结果、格式要求
→ 计算输入 Token，并记录计数方法
→ 按预算模式决定本次输出或返回容量冲突
→ 协议适配器编码请求
→ 校验最终有效载荷与计划一致后发送
→ 记录真实用量、结束原因与断点
```

### 输入计数

普通请求先做本地快速估算；接近边界或有大量工具／图像／文件时，使用该渠道支持的计数接口。原生 OpenAI Responses、Gemini、Claude 各有不同的计数协议；中转不支持时不能假定官方地址可替它计数。

本地 tokenizer 只有在型号与编码映射经过确认时才使用；否则保留“估算”标记和余量。计数缓存绑定有效输入、模型版本及渠道。不要把完整 Base64 HTTP 字节长度直接算成图片 Token，也不要把输出上限等控制字段当作模型输入。

本地估算可能过高或过低。靠近边界时应优先进一步计数；无法计数时，诊断应写“估算预算不足”，并提供调整输入工作划分或校正能力配置的途径，不称已证实超过厂商硬上限。

### 三类预算公式

| 模式 | 校验 |
| --- | --- |
| shared | 单次生成不超过已知输出上限；已知输入上限同样检查；输入＋本次生成＋合理余量不超过共享窗口 |
| separate | 输入不超过输入上限；本次生成不超过输出上限；不从输入容量里扣掉输出额度 |
| unknown | 只检查已知且有依据的约束；明确未完成全部容量验证。缺少预算关系时不能用共享公式冒充厂商规则 |

推理若包含在生成额度中，不再额外重复扣一份。缓存命中的输入仍占上下文。多轮任务累计计费用量与当前单次请求占用分别记录，不能相互替代。输出尚未指定时，不能简单把模型输入上限与输出上限相等当作共享预算证据。

自动模式可以在经确认能力内选择额度，但必须考虑任务能否完整交付；不能把剩下的几百 Token 当作足够写完整集的预算。固定模式没有空间时，应先改变合法的工作划分或返回明确冲突，不静默修改用户值。

自动模式遇到输出上限未知时，若任务已有明确数值额度，可发送该值并标记能力尚未验证；若连任务额度也没有，则返回需要补充配置的状态，提示填写固定额度、补充渠道能力或明确选择沿用服务默认。不能暗中省略参数，把自动模式变成上游默认模式。

沿用服务默认且默认值未知时，不能保证共享窗口中预留了足够输出。允许继续时必须标明这项检查未完成；高级预留是用户提供的估算依据，不是发现了服务默认。

## 四、任务和长上下文怎样处理

讨论、字段提取、剧本正文、审读具有不同的输出结构。任务层提供交付要求和可拆分的单元，模型设置提供默认偏好，二者共同生成请求计划；不要给全部任务统一写死 8K，也不要把模型最大输出当作要求每次写满。

- 讨论和字段提取：自动模式可依据结构选择较小额度，固定模式继续尊重用户值。
- 长正文：按文档、章节、分场等完整语义单元生成；需要大额度时使用经确认的渠道能力。预算不足就从完整单元拆分，不能强迫一篇长稿塞进很小的剩余额度。
- 全文审读：保留全文要求、范围及覆盖记录。超过输入能力时按原文位置分段、记录已核对范围并合并跨段问题；没有处理完全部范围就不能标记完成。摘要不能替代需要逐字核对的原稿。
- 对话与工具历史：允许去重、压缩旧过程信息，保留当前任务要求、已确认约束、最近必要交换和原文定位。精确修稿保留读取／补丁证据，不能为腾空间破坏版本和引用关系。

这些策略必须服从任务合同。当前要求每轮完整原稿的创作／审读路径，不能仅为绕过容量错误就改为只给摘要；需要修改工作划分时，必须同时设计全量覆盖和最终验收。

OpenAI 原生 compaction、Claude 上下文管理、Gemini 原生 continuation 分别作为可选能力接入。不能让它们成为通用中转的默认假设。原生思考签名、工具调用和返回的配对关系必须保持有效。

## 五、截断和恢复怎样设计

适配器把上游结果归一为明确原因：自然完成、输出额度耗尽、上下文耗尽、安全终止、工具调用、传输中断等。HTTP 200 不代表完整完成；自然结束也不代表业务资料齐全。

继续复用已有 `script-stage-continuation`、完整单元检查点和独立审读：

- 保留已闭合、合法且通过业务边界的文档／场次。
- 接续只补未完成单元，不拼接半截 JSON，不重写已保留正文。
- 正文完整但缺场次属于缺交付项，应补场次；非法场次不能当作缺场次忽略。
- 传输失败与已确定的输出截断采取不同恢复；有上游持久结果时优先读取原结果。
- 同一语义状态反复无进展时保存诊断并停止，不让恢复流程无意义循环。取消、断点和用户已有授权规则保持有效，不新增与本需求无关的统一轮数／时长硬限制。
- 只有完整结构、业务校验及所需独立审读通过后才能发布待确认草稿；确认前不写正式文档。

原生 continuation 只在对应渠道和型号明确支持时采用。例如 [Gemini long decode](https://ai.google.dev/gemini-api/docs/long-decode) 是特定 Gemini 4 Interactions 能力，不能直接用于 Gemini 3.8 或当前 Responses 中转。

## 六、运行时诊断和任务恢复

每个实际 HTTP 请求保存以下信息，页面用中文展示主要结果，技术字段放详情：

- 渠道、模型版本、协议、能力来源与版本。
- 输入 Token 数、计数方法及是否估算；共享／独立／未知预算模式。
- 最终发送的输出参数和值、来源（自动／固定／上游默认）、是否发生计划调整。
- 实际输入、总生成、推理及缓存用量。可见正文 Token 未被上游单独报告时留未知，不能用字符数或简单相减冒充精确值。
- 原始结束原因、归一原因、已保留成果和下一步接续目标。

任务开始后冻结能力和请求偏好版本。后台刷新能力目录不能改变运行中的预算或导致旧断点默默失效。恢复使用原快照；确需换渠道或额度时建立明确的新配置身份，复用内容前重新核对兼容性。

## 七、当前项目怎样分阶段落地

### 第一阶段：修正数据语义和表单

在 `packages/shared/src/models/` 新增能力结构和解析器；保留 `text_api` 负责协议请求偏好，避免把能力值直接混入 HTTP 参数。

扩展 `model-catalog.ts` 的可选能力信息，添加原生／聚合渠道的能力获取适配。未知字段不猜；无需等待所有厂商适配完成才落地核心语义。

更新 `HarnessTextModelOptions`：保持界面结构，区分能力与请求额度，显示来源及最终数值。旧 `context_window_tokens` 继续按旧共享预算行为兼容，标记为历史手工配置，不能迁移后声称是官方已验证值。旧输出与模板原样保留，未知自定义模板不强行改造成标准请求。

### 第二阶段：统一请求计划和预检

引入纯函数预算解析与 `TextRequestPlan`，替代 `text-context.ts` 的单一公式。普通、流式、工具、Anthropic、结构化兼容和后台 Responses 都消费同一计划；最终适配体再核对一次，避免中途模板覆盖。

同步 `text-tools.ts` 的上下文压力检查和 `text-request-usage.ts` 的额度预留，防止预检已经按独立预算修正，而工具压缩和累计账本仍沿旧公式决策。

### 第三阶段：计数、任务策略和恢复展示

按渠道能力接入 Token 计数、在现有业务中应用任务交付策略、完善结束原因与来源展示。复用现有语义接续，不重建一套平行的草稿生成系统。

对当前 Gemini Responses 中转，先确认渠道提供的输入／输出限制及共享关系。未确认前保持原配置可用，不因官方 Gemini 3.8 型号相同便自动切成独立预算或替换额度。

## 八、必要验收

不需要先调用真实模型试错。先用纯函数测试、模拟协议和隔离库真实业务入口验证：

1. 同一输入和输出，在共享模式拒绝、独立模式通过的边界符合预期；未知模式不伪装已验证。
2. 刷新目录不覆盖手工值；换渠道后不沿用错误来源；运行中及恢复快照稳定。
3. 三协议的固定额度准确进入实际请求，自动值可追溯，上游默认模式确实省略字段，必填协议不能漏传。
4. thinking 不重复计算，缓存不减少上下文占用，累计 Token 不被当成当前窗口。
5. 工具、Schema、历史和多媒体计数覆盖完整有效输入；计数失败不把估算伪装成精确值。
6. 自动调整可解释，固定额度不静默缩小；输入不足时不删原稿，全文审读覆盖未完成不能交付成功。
7. 截断、缺交付项、坏 JSON、非法场次、断流、无进展与取消分别走正确路径；正文哈希保持不变。
8. 工具草稿和 JSON 草稿、流式与非流式真实入口均覆盖；确认前不写正式数据。
